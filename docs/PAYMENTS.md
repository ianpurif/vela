# Stripe test checkout

VELA enables test payments only. Set `STRIPE_SECRET_KEY` to a Stripe sandbox/test secret beginning with `sk_test_`, `STRIPE_WEBHOOK_SECRET` to the endpoint's signing secret, and `NEXT_PUBLIC_APP_URL` to the application's HTTPS origin. Keep both secrets server-side. Missing configuration returns 503; live and restricted API keys are rejected. Local development may use `http://127.0.0.1:3000`, `http://localhost:3000`, or IPv6 loopback outside Vercel. Credentials, paths, query strings, and fragments are rejected in the configured origin.

The installed Stripe SDK is `23.1.0`, whose API version is `2026-10-28.endive`. Configure the webhook destination with **snapshot** payloads and that API version. Subscribe to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, and `checkout.session.expired`. Unknown signed event types and unrelated checkouts without a VELA order marker (`v_` followed by 40 lowercase hex characters in metadata or client reference) are ignored. Any event claiming a VELA ID must pass full validation. The provider recognizes current `collected_information.shipping_details` and the older top-level shipping field. See [Stripe's webhook documentation](https://docs.stripe.com/webhooks).

## Gateway boundary

`src/lib/stripe/provider.ts` exports `PaymentGateway`, `PaymentSession`, `getPaymentGateway()`, and `verifyStripeEvent(rawBody, signature)`. The gateway creates, retrieves, expires, and recovers Checkout sessions. Its normalized `expiresAt` is epoch **milliseconds**, matching the order domain; Stripe's `expires_at` is seconds. `createPaymentGateway(client, origin)` accepts a narrow SDK interface for network-free unit tests.

Checkout uses the stored order's immutable names, quantities, integer USD prices, shipping charge, and customer email. It accepts cards, collects a US shipping address, and disables Adaptive Pricing, automatic tax, and promotion codes so Stripe's amount remains equal to the saved total. This is a test checkout configuration; deployment to real payments would require separate tax and shipping-policy decisions. Product changes after order creation do not change the Checkout amount. Return URLs carry only the encoded order ID; visiting either redirect does not prove payment or release inventory.

For this API version the create parameter is `allowed_payment_method_types: ["card"]`, which limits dynamically eligible methods to cards. Enable cards in the Stripe test dashboard; the allowlist does not force a disabled method to become eligible. Returned sessions containing other payment methods are rejected. The older `payment_method_types` create parameter is absent from the installed types. See [the current Checkout create parameters](https://docs.stripe.com/api/checkout/sessions/create).

Every create uses the order ID as Stripe's idempotency key and exactly the same order-derived parameters. The gateway checks the returned test mode, metadata `orderId`/`userId`, `client_reference_id`, total, currency, and expiration against the snapshot. Requests use a 10-second timeout and at most two SDK network retries. A provider exception remains an uncertain result and exposes no upstream request or credential details. See [idempotent requests](https://docs.stripe.com/api/idempotent_requests).

Stripe permits explicit session expiry from 30 minutes to 24 hours after creation. VELA uses a 35-minute hold and stops new creates once less than 30 minutes remain. Retrying must preserve the original expiration; do not extend it to satisfy Stripe or alter parameters under an existing key. A session can only be explicitly expired while open. See [Checkout creation](https://docs.stripe.com/api/checkout/sessions/create) and [session expiration](https://docs.stripe.com/api/checkout/sessions/expire).

## Unattached session recovery

A process can stop after Stripe creates a session but before its ID reaches Firestore. A missing `sessionId` therefore does not establish that payment is impossible. `findSession(order)` lists all sessions created from 60 seconds before order creation through 60 seconds after its expiry, without filtering by session status. It paginates to the end and checks both metadata and client reference. A complete, expired, or open match is returned for the order service to reconcile.

Two matches, conflicting metadata, API errors, repeated/invalid pagination, or reaching the 100-page limit all fail closed. They never produce a false absence result. The limit permits at most 10,000 sessions per recovery scan; high-volume windows require operator reconciliation rather than releasing a hold. A `null` result means only that a successfully exhausted scan found no match at that time. Release after an unattached create must also wait until the order has expired plus the service's safety delay and fresh creation attempts have stopped. The existing order and reservation remain the source of truth during uncertainty. See [Stripe session listing and its pagination parameters](https://docs.stripe.com/api/checkout/sessions/list).

## Webhook verification

The handler must read `await request.text()` once and pass that untouched body plus `Stripe-Signature` to `verifyStripeEvent`. The official SDK verifies the signature and its default five-minute timestamp tolerance before application code reads the payload. Missing/invalid signatures and signed live events return 400. A valid signature authenticates delivery; fulfillment still requires a matching stored order, test session, paid status, expected amount/currency, and the service's atomic duplicate-event guard. Duplicate and out-of-order delivery must not deduct inventory twice. Never mark paid from a redirect, browser payload, retrieve response, or API create response. [Stripe requires the raw body for signature verification](https://docs.stripe.com/webhooks#verify-webhook-signatures-with-official-libraries).

## Verification status

`tests/stripe-provider.test.ts` uses an injected SDK client and the official SDK's generated test signatures. It performs no external requests and needs no real credentials. It covers fixed amounts/parameters, return origins, test-only keys and events, shipping normalization, exhaustive recovery, ambiguous matches, paging failures, and signature rejection. Successful local unit tests do not establish external Stripe integration. A real test-mode Checkout payment, decline, duplicate webhook replay, and expiry must still be exercised with configured Stripe test credentials and a webhook listener before claiming that verification.
